## The biggest SEO win is not another Sphinx plugin

**Melder needs to explain its capabilities in the language developers search for, before introducing Melder’s own terminology.** The underlying documentation infrastructure is fairly strong. The weaker part is the search-facing presentation: the homepage leads with a slogan, several useful guides have vague titles, and some important tutorial pages are short README extracts rather than complete answers. ([Melder][1])

I inspected the live docs and the `prod` branch’s Sphinx configuration, documentation generators, manifests, and validation scripts. The terminal `git clone` failed because this environment could not resolve GitHub, so I retrieved the source through the connected GitHub service instead. **I did not run a complete Melder/Sphinx build or inspect your Search Console data.**

I also made a **[Melder SEO starter kit](sandbox:/mnt/data/melder-seo-starter.zip)** containing a homepage patch, a generated-HTML SEO checker, nine passing synthetic tests, and implementation instructions. Nothing was pushed to your repository.

Here is where I would put the effort, in order.

## 1. Fix the homepage’s title and positioning first

The current homepage title is:

> A runtime you can build on — Melder — a runtime you can build on

That repeats the slogan without identifying the Python problem the project solves. The source of the repetition is the homepage heading combined with `html_title` in `docs/conf.py`. ([Melder][1])

**Keep the slogan. Stop making it do the job of a product description.**

Your architecture documentation gives you a much stronger positioning statement: Melder is a dependency graph runtime, with dependency injection as an entry point and a retained graph that supports lifecycle management, inspection, and more advanced operations. That is more specific than “a runtime,” without reducing the project to just another DI container. ([Melder][2])

### Change `docs/conf.py`

Use a short sitewide suffix:

```python
html_title = "Melder"
```

Then let individual page titles carry the topic. Google recommends descriptive titles and avoiding repetitive boilerplate; there is no universal character count that makes a title correct. ([Google for Developers][3])

### Give `docs/index.md` a search-facing opening

My suggested opening:

```markdown
---
myst:
  html_meta:
    description: >-
      Melder is a Python dependency graph runtime with constructor injection,
      scoped lifetimes, cleanup, and runtime inspection. Explore runnable examples.
---

(a-runtime-you-can-build-on)=
# Python dependency injection and dependency graph runtime

**Melder — a runtime you can build on.**

Melder wires ordinary Python classes, functions, and instances into a live
dependency graph. Start with constructor dependency injection, explicit
instance lifetimes, and scoped cleanup. Add runtime inspection, isolated
worlds, and agent-operated infrastructure when your application needs them.

**Python 3.14+. Zero runtime dependencies.**
```

The MyST `html_meta` frontmatter is supported syntax for emitting a real HTML description. The explicit heading target preserves the old homepage fragment rather than needlessly breaking links to it. ([MyST Parser][4])

This should produce a substantially clearer HTML title:

> Python dependency injection and dependency graph runtime — Melder

That is the intended HTML title, not a guarantee that Google will display it unchanged. Google can construct a different title link. ([Google for Developers][3])

**Important distinction:** the description is useful snippet copy, not a direct ranking boost. Write an accurate reason to visit the page; Google may still select a passage from the body instead. ([Read the Docs Documentation][5])

## 2. Turn your strongest existing topics into standalone answers

I would not start by publishing another hundred pages. I would improve the pages that already map to recognizable developer problems.

These are **search-intent hypotheses**, not claims about measured keyword volume:

| Existing route                      | Proposed title                                                         | What the page should answer                                                             |
| ----------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `beginner/dependency-injection`     | **Python constructor dependency injection with type hints**            | How do I wire ordinary classes together without constructing every dependency manually? |
| `beginner/lifetimes`                | **Python dependency lifetimes: shared, scoped, and transient objects** | When is an instance reused, and when is a new one created?                              |
| `beginner/cleanup`                  | **Python resource cleanup and dependency ownership**                   | Who closes resources, and when does teardown happen?                                    |
| `intermediate/dependency-injection` | **Explicit and collection dependency injection in Python**             | What happens when a type annotation is insufficient or I need multiple implementations? |
| `intermediate/overrides`            | **Overriding Python dependencies with Melder**                         | How do I substitute part of an object graph without rebuilding the application by hand? |
| `advanced/worlds`                   | **Isolating multiple Python object graphs in one process**             | How do independent subsystems maintain separate runtime state?                          |

These routes already exist in your curriculum. **Improve their titles and content without changing their URLs.**

### The constructor-injection page is the clearest immediate opportunity

The current beginner page provides a short explanation and a code fragment, but the fragment assumes definitions such as `Database` and `book`. It is useful within the broader tour, but it is not yet a satisfying standalone landing page for someone arriving from search. ([Melder][6])

My recommended rewrite would walk through one complete application:

Start with manual construction of two or three ordinary classes. Show the maintenance problem when the graph grows. Then show the complete Melder equivalent—including imports, class definitions, registration, `conjure`, resolution, and an assertion that demonstrates the result.

After that, explain why the constructor annotation resolves the intended dependency, how instance lifetime affects the example, and what to do when resolution fails. End with contextual links to explicit injection, lifetimes, and cleanup.

**Make the page independently useful.** A visitor should not need to reconstruct the example from three other pages before understanding the answer.

Do not pad it to a target word count. Google explicitly says it has no preferred word count; completeness and usefulness are the point. ([Google for Developers][7])

### Separate your two dependency-injection guides

There is a concrete source-level overlap: both beginner and intermediate dependency-injection chapters use the same README section. The beginner version stops at an `end_before` marker; the intermediate version includes more of that section.

I would give them distinct jobs:

**Beginner:** a complete constructor-injection tutorial.

**Intermediate:** explicit dependency selection, collection injection, and situations where annotations alone are insufficient.

This is not a claim that you are suffering a “duplicate-content penalty.” It is an editorial opportunity: make each URL answer a clearly different question.

### Translate lifecycle terminology carefully

Your lifecycle page already has useful substance. Keep the exact Melder semantics, but introduce them through familiar concepts such as instance reuse, transient construction, and scope boundaries. Do not casually describe `unique` as an unrestricted process-global singleton when its frame boundary matters. ([Melder][8])

That combination—recognizable terminology followed by precise project-specific behavior—is much better than either keyword stuffing or unexplained internal vocabulary.

## 3. Make improvements in the actual source model—not generated files

This repository has a custom documentation assembly pipeline. Advice that simply says “edit the Markdown in the build directory” or “run Sphinx directly over `docs/`” would miss how it works.

`DocumentationBuilder.prepare()` rebuilds `docs/_build/source` from authored pages, README selections, and generators. **Anything edited in that generated source tree will be overwritten.**

### Use an authored source file for the expanded beginner guide

Your curriculum loader already supports choosing either a README section or an authored source file—but requires exactly one of those choices.

Replace the existing chapter entry in `docs/curriculum.toml` with something like:

```toml
[[chapter]]
id = "beginner/dependency-injection"
title = "Python constructor dependency injection with type hints"
level = "beginner"
source = "beginner/dependency-injection.md"
lessons = ["intermediate:15", "beginner:16"]
```

Then create `docs/beginner/dependency-injection.md` with the complete tutorial and its own metadata.

**Replace the old entry; do not append a second chapter. Remove both `readme` and the old `end_before` setting.** Keep the same `id` so the public URL remains stable.

### Improve example titles through the existing override mechanism

Your example generator derives default titles from filenames using:

```python
path.stem[3:].replace("_", " ").capitalize()
```

That is a reasonable fallback, but filenames are not necessarily good search-result titles. The generator already supports editorial title overrides.

For example, add an override in `docs/catalog.toml`:

```toml
[[lesson]]
source = "UX_and_AIX_experiences/01_beginner/02_lifecycles_unique_vs_many.py"
title = "Shared and transient Python objects: unique vs many"
```

Do not change the lesson `id` just to improve its title. You can improve the visible heading without moving the URL or renaming the runnable source.

### Generate descriptions deliberately

The existing lesson model contains a title, goal, public surfaces, and topics, but no dedicated description field; `_lesson_body()` does not emit description metadata.

My recommendation is to add an optional editorial description to the model and renderer. Use a cleaned, accurate goal summary as a fallback only where it reads naturally.

**Adding `description = "..."` to TOML alone will do nothing unless the loader and renderer consume it.**

Start with the homepage and the highest-value guides, then extend the metadata coverage. Google explicitly allows programmatically generated descriptions when they are accurate, readable, and page-specific. Avoid one generic description copied across every example. ([Google for Developers][9])

## 4. Add task-oriented navigation without breaking the curriculum

Your four learning levels are useful for someone studying Melder. They are not the only useful way to enter the docs.

Also, the builder explicitly enforces the four level names and their order. I would not casually rename those labels as an SEO tweak.

Instead, add a homepage section such as **“Solve a Python application problem”** with direct links to constructor injection, instance lifetimes, cleanup, overrides, and isolated object graphs.

Use link text that explains the destination. “Manage dependency lifetimes” tells a new reader more than “Learn more.” Descriptive, contextual links are also what Google recommends. ([Google for Developers][10])

There is something you should **preserve** here: the example catalog already emits static HTML cards with ordinary links, and its JavaScript filters that existing list. It is not a catalog whose links only appear after JavaScript execution.

So the recommendation is not “make the catalog crawlable.” It is **make the most valuable routes easier to understand and reach**.

## 5. Verify your existing canonical and sitemap system—do not replace it blindly

You already have:

```python
html_baseurl = os.environ.get("READTHEDOCS_CANONICAL_URL", "")
```

And your custom builder already generates a page-level `sitemap.xml` from declared documentation pages when the canonical base is supplied. **You do not need another sitemap extension merely because an SEO checklist mentions one.**

Three details deserve attention.

### The canonical environment variable is version-specific

Read the Docs supplies a canonical base for the version being built. That is not the same as automatically consolidating every release, `/latest/`, and `/stable/` into one preferred version. ([Read the Docs Documentation][11])

Decide which version should be the main entry point for new users. Then verify how genuinely duplicate aliases are handled.

Do **not** blanket-canonicalize all historical documentation to the latest version when the content differs. Do not point every page’s canonical at the homepage. Canonicals should identify the corresponding preferred page, not erase the distinction between topics. Google treats canonical declarations as signals, not absolute commands. ([Google for Developers][12])

### Your custom sitemap can replace the default RTD sitemap

Read the Docs documents that a custom sitemap in the default version can be served at the domain root instead of its automatically generated sitemap. Your builder’s sitemap lists the current build’s declared pages. Check that this matches your intended version policy. ([Read the Docs Documentation][13])

### RTD search settings are not Google settings

Your `.readthedocs.yaml` boosts beginner pages and ignores `_modules/*` and `_sources/*` for search. Those settings control **Read the Docs search**. They do not boost Google rankings or instruct Google not to index those paths.  ([Read the Docs Documentation][14])

The deployment checks I would make are:

* Inspect the final HTML canonical and robots directives on the homepage, a guide, an example, and an API page.
* Inspect the served root sitemap and confirm its URLs match the intended host, version, and URL format.
* Use Search Console URL Inspection to compare the declared canonical with Google’s selected canonical.

**I could not verify the live robots file, sitemap responses, or response headers here. That is an unverified area—not evidence that those endpoints are broken.**

## 6. Add an SEO regression check to your existing documentation tests

Your current `check_site.py` is doing useful work: local links, fragments, duplicate IDs, image alt attributes, declared-page coverage, and source-download fidelity. It does not check page titles, descriptions, canonical tags, or robots metadata.

The checker in the starter kit complements that system. It checks generated content pages for missing or duplicate titles, description coverage, canonical consistency, accidental `noindex`, and sitemap destinations.

It uses Python’s standard library and does not add a runtime dependency to Melder.

After copying it to `docs/tools/check_seo.py`, run it through your actual build pipeline:

```bash
python -m pip install -r docs/requirements.txt
python -m unittest discover -s docs/tests -q
python docs/tools/build_docs.py check

# For this local/CI audit. On RTD, keep its platform-provided value.
export READTHEDOCS_CANONICAL_URL="https://melder.readthedocs.io/en/latest/"

python docs/tools/build_docs.py build
python docs/tools/check_site.py

python docs/tools/check_seo.py docs/_build/html \
  --base-url "$READTHEDOCS_CANONICAL_URL" \
  --require-description index.html \
  --json docs/_build/seo-report.json
```

Initially, require a description only on the homepage. After adding descriptions to a whole group, require that group too:

```bash
--require-description 'beginner/*.html'
```

This gives you a manageable rollout instead of turning every missing description into a deployment failure immediately.

**Test status:** all nine synthetic checker tests passed. The homepage patch was checked against reconstructed excerpts of the inspected source, not a complete checkout. Run `git apply --check` and the real repository build before adopting it.

The checker also assumes version-local self-canonicals and publicly indexable content. Review intentional exceptions before making it a release gate; do not run it unchanged against intentionally noindexed preview builds.

## 7. Build discovery around evidence only Melder can provide

Metadata helps explain a page. It is not a substitute for giving someone a compelling reason to read or reference it.

My strongest content recommendation beyond the introductory guides is a **worked comparison of dependency-lifetime and ownership behavior**, using actual code and clearly stated tradeoffs.

Your benchmark dependency group already includes Dependency Injector, Dishka, Injector, and Lagom. That creates an obvious research direction, but it is not evidence that Melder outperforms any of them.

A useful comparison would show equivalent workloads, setup requirements, interpreter and package versions, lifecycle semantics, and reproducible commands. Any performance claims should distinguish startup/graph construction from resolution and cleanup. Publish the cases where Melder is a poor fit as clearly as the cases where it helps.

Other promising original pieces would be a complete scoped-resource example or a walkthrough of inspecting a retained dependency graph. Those are more distinctive than another generic “What is dependency injection?” article.

This recommendation follows Google’s emphasis on original information, demonstrable experience, and content that adds value beyond summarizing what already exists. It is not a promise of backlinks or rankings. ([Google for Developers][7])

### Measure qualified discovery, not just visits

Use Search Console to establish which pages and queries already receive impressions before deciding which topic to expand next. The RTD SEO guide also recommends connecting search and traffic measurement rather than relying solely on on-page changes. ([Read the Docs Documentation][5])

My suggested measurement plan is to separate branded queries from non-branded problem queries, and group pages into guides, examples, API reference, and architecture. Compare similar reporting periods once enough data exists.

For adoption signals, track actions such as opening the runnable example, downloading a collection, or clicking through to the repository. Treat those as **proxies for developer interest**, not proof that someone successfully installed or adopted Melder.

## What I would not spend effort on yet

I would not migrate away from Read the Docs, rename every `.html` URL, install overlapping SEO extensions, or write hundreds of lightly differentiated articles before fixing the existing entry pages.

I would also keep AI-search work proportionate. Google says its AI search features do not require special AI text files or special schema beyond the usual requirements for eligible, useful search content. An `llms.txt` project may have other purposes, but it is not the missing prerequisite for visibility in Google’s AI features. ([Google for Developers][15])

**My priority order is: homepage title and opening → complete constructor-injection and lifecycle guides → distinct page intent and task navigation → generator-backed metadata → deployment verification and regression checks → original, reproducible comparison content.**

The most valuable immediate change is simple: **make a Python developer who has never heard of Melder understand what it does, land on a complete answer, and run a working example.** Your source-backed documentation system is already a good foundation for that.
